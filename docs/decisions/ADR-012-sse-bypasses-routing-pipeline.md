# ADR-012：SSE 流式路径直连 ChatClient，不经意图识别/路由/编排管线

## 背景

`/api/agent/chat/stream`（`SseController`）自阶段一起直接调用 `ChatClient.stream()`，与 `/api/agent/chat`（`AgentController` → 意图识别 → 路由 → ReAct/PlanAndSolve/Supervisor）是两条独立路径。规划审查时曾评估"SSE 是否也应接入路由管线"，同时发现三个工程缺陷：流异常时客户端收不到任何终止信号、无心跳导致长思考间隙易被网关断连、请求日志全量记录用户消息存在泄露风险。

## 决策

1. **SSE 保持直连 ChatClient**。理由：
   - 路由管线的执行器（ReAct 迭代、PlanAndSolve 分步、Supervisor 编排聚合）均为**阻塞式同步语义**，产出一次性 `AgentExecutionResult`；将其包装成流式需要在管线内部引入响应式边界，改动面大且违背各执行器的超时/重规划设计。
   - 流式场景的用户诉求是"尽快看到逐步输出"，在意图识别（含 L4 LLM 兜底调用）之后再开始推送会显著增加首 token 延迟。
   - 因此同步走管线（`/chat`）、流式直连（`/chat/stream`）是刻意的双路径设计，而非遗漏。
2. **错误终止事件**：流式调用异常时 `onErrorResume` 降级推送一次 `[ERROR] 流式回复生成失败，请稍后重试`，随后照常发送 `[DONE]`；完整异常堆栈只记录到服务端日志（含 conversationId），不外泄给客户端。
3. **15 秒心跳**：主流空闲期间每 15 秒推送一次 SSE 注释行（`:heartbeat`），防止代理/网关因长时间无数据切断连接；主流结束（含异常降级）后心跳通过 `takeUntilOther` 自动停止。主流经 `publish().autoConnect(2)` 共享，保证 ChatClient 流式调用只订阅一次。
4. **日志脱敏**：请求日志中的用户消息截断至前 50 字符；`AgentController` 同步路径本就只记录元数据（conversationId、hasConfirmationToken、执行结果指标），无需改动。

## 备选方案

- **SSE 也走路由管线**：需在三个执行器内部打通响应式流，意图识别前置会抬高首 token 延迟，放弃。
- **心跳由客户端超时重连代替**：依赖每个客户端正确实现重连退避，且无法阻止中间网关主动断连，放弃。
- **错误详情透传给客户端**：异常消息可能包含内部主机/模型配置信息，放弃；客户端只收到通用文案。

## 影响

- 客户端需识别四类事件：内容片段、`[ERROR] ` 前缀错误事件、`:heartbeat` 心跳注释行、`[DONE]` 终止标记
- 流式路径不具备意图识别、安全门确认、多 Agent 编排能力；高危操作请使用同步 `/chat` 接口
- 日志中不再出现完整用户消息（最长 50 字符摘要）
- 测试：`SseControllerTest` 覆盖错误终止事件、心跳节奏（测试构造器注入短心跳间隔，真实时钟验证）、长消息截断路径
